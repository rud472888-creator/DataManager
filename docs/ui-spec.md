# Remote Web Console UI Spec

Working root: `~/desktop/datamanager`.

## UI Role

The remote web console is a browser command and monitoring surface for the macOS local runtime. It does not execute file operations. It displays runtime-provided sources, destinations, jobs, logs, errors, and reports through REST and WebSocket data.

## Screen Inventory

| Screen | Purpose | Primary action |
|---|---|---|
| Home | Runtime status, active job summary, volume status, recent jobs | New offload job |
| New Job | Choose runtime-discovered source and allowed destinations, set project metadata | Create job |
| Job Detail | Progress, current file, speed, ETA, warnings, errors, logs | Pause, cancel, open reports |
| Queue | Queued, paused, warning, failed, and recent jobs | Resume or retry when allowed |
| Reports | Read generated report list and open/download runtime-served artifacts | Open report |
| Settings | Token status, allowed destinations view, dependency status | Save supported settings |

## Screen Responsibilities

### Home

- Show runtime online/degraded/offline state, version, dependency/capability summary, active job, recently completed jobs, and volume health.
- Primary action: `New offload job`.
- Empty state: no active job, no volumes, or runtime unavailable.
- Error state: explain that the browser is disconnected from the local runtime, not that work necessarily stopped.

### New Job

- Show runtime-discovered source volumes and allowed destination IDs.
- Collect project name and supported policy options.
- Do not expose browser file inputs, drag/drop media import, or raw arbitrary destination path writes.
- Disabled state explains missing runtime, missing source, missing destination, or single-active-job policy.

### Job Detail

- Show state, step, current file, file counts, byte counts, speed, ETA, warnings, errors, and recent events.
- Command buttons appear only when allowed by the current state. Rejected command results are displayed as runtime decisions.
- Report links appear only after runtime reports are registered.

### Queue

- Group queued, paused, warn, failed, completed, cancelled, and active jobs.
- Make recoverable states visually distinct through background fill and status text.
- Retry/resume actions must explain that the local runtime decides whether the request is accepted.

### Reports

- Show checksum PDF, image PDF, metadata XLSX, and manifest JSON when generated by the runtime.
- Missing artifacts show pending/unavailable reasons.
- Browser opens runtime-served links; it does not build reports.

### Settings

- Show token status, allowed destination roots by runtime-managed label, dependency status, and UI preferences.
- Do not provide direct source/destination filesystem pickers.

## State Inventory

- Runtime: online, degraded, offline, dependency-unavailable.
- Job: queued, scanning, preparing, copying, pausing, paused, verifying, parsing, capturing, reporting, warn, failed, cancelled, completed.
- Data: empty, loading, loaded, stale, error.
- Command: idle, pending, accepted, rejected, failed.
- Connectivity: connected, reconnecting, disconnected.
- Capability: available, unavailable, unknown.
- Report: not-started, generating, ready, failed, unavailable.
- Volume: available, missing, busy, read-only, low-space.

## Action Hierarchy

| Context | Primary | Secondary | Destructive |
|---|---|---|---|
| Home | New offload job | Refresh runtime | None |
| New Job | Create job | Reset form | None |
| Copying job | Pause | Refresh logs | Cancel |
| Paused job | Resume | Refresh logs | Cancel |
| Warn/failed job | Retry | Open logs/reports | None |
| Completed job | Open reports | View logs | None |

Destructive actions require clear labels and runtime confirmation/rejection feedback.

## Layout Intent

- First viewport must expose the current runtime context and an obvious primary CTA.
- Use Gutenberg-style priority: context and status near the upper-left, primary action visually prominent toward the lower-right or equivalent mobile action location.
- Field-pressure scanning matters more than decoration.
- Use dense but readable operational layouts, not marketing sections.

## Visual Language

- Black and white first, with limited semantic accents only when needed for warning/error/success.
- No shadows. Use lines, spacing, weight, and fill to create hierarchy.
- Selected states must change background, not border only.
- Border radius should be restrained; outer radius is twice the inner radius when nested geometry is unavoidable.
- Avoid generic card soup. Cards are for repeated items or framed tools, not every section.

## Design Tokens

| Token | Purpose |
|---|---|
| `--bg` | app background |
| `--fg` | primary text and primary button fill |
| `--muted` | secondary text |
| `--line` | dividers and borders |
| `--fill` | neutral filled panels |
| `--selected` | selected row/card background |
| `--warn` | warning text/fill, limited use |
| `--danger` | destructive/error text/fill, limited use |
| `--ok` | success text/fill, limited use |

No page should depend on one hue family or decorative gradients.

## Responsive Rules

- Mobile and iPad views must keep the primary action reachable in the first viewport.
- Use a bottom action bar or an equally obvious first-card CTA on small screens.
- Tables must degrade to compact rows or grouped cells without horizontal overflow for critical status.
- Controls must remain keyboard reachable and labeled.
- Desktop can show overview, active job, and logs side by side.
- Mobile stacks status first, then current job, then actions, then logs/reports.
- Long filenames, error messages, and report names must wrap or truncate without overlapping adjacent controls.

## Accessibility Requirements

- Use semantic headings, regions, lists, buttons, forms, and status text.
- Provide visible focus states.
- Keep contrast high in the black/white system.
- Do not rely on color alone for job state.
- WebSocket changes that affect current work should be represented in accessible status text.

## Forbidden UI Capabilities

The web console must not offer a browser local file picker for source or destination paths. It must not imply it is copying, checksumming, parsing, or directly writing files. Labels should say the local runtime is executing work and the console is sending requests or showing state.
